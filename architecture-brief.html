FastAPI · LlamaIndex · Qdrant · BGE-M3 · DeepSeek

Routes never talk to LlamaIndex or Qdrant.

This is a production-shaped PDF Q&A API. The interesting part is not “we used RAG.” It is a clean layered FastAPI app with three retrieval modes, SHA-256 dedup, page-at-a-time ingestion, and a two-stage retrieve-then-rerank path that cites pages.

30-second opener

“I built a FastAPI PDF RAG service. Upload streams PDFs to disk, chunks with LlamaIndex, embeds locally with BGE-M3 into Qdrant. Questions go through hybrid search — dense vectors plus BM25, fused with RRF — then a BGE cross-encoder reranker, then DeepSeek. Sync and SSE chat, async ingest with task polling. Abstractions sit under every vendor so routes only call services.”

What it is

A single FastAPI process that answers questions over uploaded PDFs using retrieval-augmented generation. Default path is hybrid + rerank. Local embeddings and reranker (Apple Silicon MPS / CUDA / CPU). Remote LLM via OpenAI-compatible DeepSeek API with thinking disabled.

What it is not: multi-tenant SaaS, a chatbot with history, an agent graph, or OCR. Those are on the README roadmap, not in the code.

What we actually run

Two processes we start. One API we call. docker compose up is exactly that: app (port 8000) and qdrant (6333 HTTP / 6334 gRPC). There is no Redis, no Celery, no extra embed server, no second worker.

Your browser talks only to :8000. That process embeds, reranks, and keeps BM25. It talks to Qdrant for vectors and to DeepSeek for the answer text. HuggingFace models are files on disk inside the app, not a third server.

Call tree

upload.py _stream_to_disk # 8 MB aiofiles chunks IngestService.upload_pdf_from_file Path.name PDF check, max size SHA-256 in to_thread (64 KB blocks) StreamingIngestionPipeline.ingest_pdf find_by_hash → duplicate? return existing id, chunks=0 PdfReader, page by page skip empty text SentenceSplitter(512, 64) batch 16 → embed_texts → upsert_chunks task_manager progress if task_id always unlink temp file (finally) invalidate_bm25 unless duplicate

Dedup is content hash, not filename. Hash lives on every chunk payload. Payload indexes on document_id and content_hash so filters are not full scans.

Delete is Qdrant delete(points_selector=Filter) — not scroll-then-delete, which would truncate at the scroll limit. Delete also invalidates BM25.

Qdrant HNSW — we do not rebuild per delete

Our app never rebuilds the vector index. Qdrant soft-deletes: a bitmask marks the point gone, so search cannot return it immediately. The HNSW graph may still hold the vector on disk until the Vacuum Optimizer rebuilds that segment in one go — default when ≥20% of the segment is deleted (deleted_threshold: 0.2) and the segment has ≥1000 vectors (vacuum_min_vector_number). Tiny collections may never vacuum; search is still correct.

Query pipeline — three modes

Toggle the mode you will walk them through. Defaults in this repo: hybrid + rerank.

top_k 10 retrieval_top_k 20 vector_top_k 10 bm25_top_k 10 fusion_top_k 15 final_top_k 5
1. QuestionChatRequest.question (min length 1) → ChatService → QueryEngine
2. EmbedBGE-M3, L2-normalized, dim 1024, under asyncio.Lock (SentenceTransformer is not concurrent-safe)
3. DenseQdrant query_points, cosine. Missing collection → empty list, not 500.
4. BM25In-memory BM25S over a full collection scroll. Lazy-built, double-checked lock.
5. RRFLlamaIndex QueryFusionRetriever mode reciprocal_rerank, num_queries=1 (no LLM query rewrite)
6. RerankCross-encoder scores (query, chunk) pairs. This is usually the slow local step. Returned score is the logit, not cosine.
7. ContextDedup sources by (filename, page). Shared citation numbers. Prompt: “use only the context.”
8. LLMDeepSeek V4 Flash, temp 0, thinking disabled, sync or token stream.

Empty retrieval short-circuits: “No relevant documents found…” — never calls the LLM.

Why hybrid + RRF

Dense (BGE-M3) catches paraphrases: “auth code grant” ≈ “authorization code flow.” BM25 catches exact tokens the embedder can smear: error codes, RFC numbers, function names, “OAuth 2.0.”

Reciprocal Rank Fusion does not mix raw scores (cosine vs BM25 are incomparable). LlamaIndex QueryFusionRetriever mode reciprocal_rerank — we do not set k; the library hardcodes k = 60 (Cormack et al.). Then similarity_top_k=15.

score(chunk) = Σ 1 / (60 + ranklist)
e.g. dense #1 and BM25 #3 → 1/61 + 1/63 ≈ 0.0323
only in one list → one term; still eligible. Sort, keep 15.

Why num_queries=1

Fusion can generate extra queries with an LLM. We set LlamaSettings.llm = None at startup (tests too) so LlamaIndex cannot fall through to OpenAI. num_queries=1 means “fuse these retrievers, do not rewrite the question.” Mention this — it shows you read the wiring, not just the README.

BM25 is not Qdrant sparse vectors. It is an in-process index rebuilt after ingest/delete via invalidate_bm25(). First query after a cold start or invalidation scrolls up to 100k points. Say that limit out loud if they ask about scale.

The three models

RoleModelWhereWhy this one
Embedding (bi-encoder) BAAI/bge-m3 local, SentenceTransformer 1024-d multilingual, encode query and docs independently — fast ANN
Reranker (cross-encoder) BAAI/bge-reranker-v2-m3 local, transformers Sees query and chunk together. Accurate, expensive — so only on ~15–20 candidates
Generator deepseek-v4-flash API, AsyncOpenAI Cheap/fast generation. extra_body={thinking:{type:disabled}} so we don’t wait on chain-of-thought

float16 on MPS/CUDA, float32 on CPU. Reranker uses torch.inference_mode() and a threading lock. Embeddings use an asyncio lock. Device: utils/device.py prefers MPS, then CUDA, then CPU.

What a point looks like

Collection: cosine, size 1024. Point id = chunk UUID. Payload:

{ "chunk_id": "uuid", "document_id": "uuid", // all chunks of one PDF "filename": "oauth.pdf", "page_number": 17, "text": "…chunk…", "content_hash": "sha256…" // same on every chunk of that file }

Dense search uses the vector. BM25 uses text after a scroll — same payload, different index. List documents scrolls (limit 100k), groups by document_id, counts chunks, takes max page. There is no separate document table — Qdrant is the registry.

Concurrency and ops details they love

  • Don’t GC background tasks: ChatService / IngestService keep a set[asyncio.Task] and discard on done.
  • Sync Qdrant + torch run in asyncio.to_thread so the event loop stays free.
  • TaskManager is a process-local dict + threading.Lock, TTL 24h, pruned on create. Lost on restart. Not safe with multiple uvicorn workers.
  • Health does not ping Qdrant or DeepSeek.
  • Docker: app + Qdrant 1.12, healthcheck, uploads volume, QDRANT_HOST=qdrant. Image is Python 3.14-slim; CI tests 3.12.
  • Latency log line: mode=hybrid embed=… dense_search=… bm25=… rerank=… llm=… total=… retrieved=… final=…

Honest gaps (say these before they find them)

  • No auth, no multi-tenancy, no chat history.
  • No OCR — digital text only. Scanned PDFs become empty pages, skipped.
  • Task state is RAM. Restart or a second worker = lost jobs / split brain.
  • BM25 and list-documents scroll cap at 100k points.
  • /health is not a dependency check.
  • Hybrid retriever constructs its own QdrantClient for BM25 scroll, separate from QdrantVectorStore.
  • README roadmap still lists “unit tests / CI” — they actually exist (.github/workflows/ci.yml, pytest markers). Don’t undersell that.

Interview answers

Filter as they talk. Each card is a thing you should be able to say in your own words.

What is RAG, in this project?

Retrieve relevant PDF chunks, stuff them into a prompt, generate. The LLM is not the knowledge store — Qdrant is. That cuts hallucination and gives page citations.

Why RAG instead of fine-tuning?

PDFs change per user, we need citations, and we cannot retrain when a file is uploaded. RAG updates the index; the generator stays a general model.

Why retrieve then rerank?

Bi-encoder embeds query and docs separately so we can ANN-search millions of chunks. Cross-encoder reads the pair and is much better at relevance, but O(n) forward passes. So: cheap recall of 15–20, expensive precision down to 5. Classic two-stage IR.

Why hybrid search?

Embeddings miss rare tokens. BM25 misses paraphrases. RRF merges ranks without pretending cosine and BM25 scores share a scale.

Explain RRF in one sentence.

Rank-only: score = Σ 1/(60+rank) from dense and BM25. LlamaIndex hardcodes k=60; we take top 15, then the cross-encoder cuts to 5. Never add cosine to BM25.

Why cosine + normalize_embeddings=True?

BGE-M3 is trained for cosine. L2-normalizing makes cosine equivalent to dot product, which Qdrant cosine distance expects. Unnormalized vectors would distort nearest neighbors.

What chunking did we use?

Page-bounded sentence splitting. Each PDF page is one LlamaIndex Document, then SentenceSplitter(512, 64). Not character windows, not LangChain recursive, not semantic chunking. Chunks never cross a page, so “page 17” is true.

Why chunk 512 with overlap 64?

Small enough to be specific, large enough for a sentence of context. Overlap reduces the “answer split across a boundary” miss. SentenceSplitter keeps linguistic boundaries vs naive character windows.

Is that chunking good?

Good default for cited PDF Q&A. Sentences stay intact, pages stay honest, 512 fits the reranker’s 1024 max length. Weak on tables/code, and an idea that continues on the next page is still split. Keep it until recall@k says otherwise; next step is heading-aware, not jumping to semantic chunks that blur page numbers.

How do you detect duplicate PDFs?

SHA-256 of file bytes, stored on chunk payload, looked up with a payload index. Same bytes, different name → existing document_id, chunks 0, no BM25 rebuild.

How does BM25 relate to Qdrant?

Qdrant is not running BM25. We scroll payload text (up to 100k points), build an in-process BM25S index on that snapshot, and keyword-rank chunks. Dense still uses Qdrant HNSW. RRF merges the two lists. Duplicate uploads skip the rebuild because the corpus did not change.

Why invalidate BM25 after ingest/delete?

BM25 is a snapshot of the corpus in RAM. If we don’t bust it, new PDFs are invisible to keyword search and deleted ones still rank.

Does the BM25 index stay while the app runs?

Yes — in the FastAPI process, until ingest/delete drops it. Next chat rebuilds from Qdrant. Restart or a second uvicorn worker: gone. Qdrant on disk is durable; BM25 is a hot cache.

Do we keep chat history?

No. API is {"question": "..."} only. Each turn is retrieve + generate. The UI may show old bubbles in the browser; those are not sent back. Follow-ups only work if the PDFs still retrieve the context. Roadmap item, not built.

Why LlamaSettings.llm = None?

LlamaIndex defaults to OpenAI. Fusion retriever would try to spawn an LLM for query generation. We own DeepSeek ourselves and do not want a hidden OpenAI dependency. Tests set the same thing.

Why disable thinking on DeepSeek?

V4 Flash can emit a reasoning channel. For RAG we want grounded answers fast, not a hidden chain-of-thought that adds latency and can ignore the context. extra_body={"thinking":{"type":"disabled"}}.

Why temperature 0?

We want extractive, repeatable answers from context, not creative drift. RAG evaluation is easier when generation is greedy.

How do you ingest a 1 GB PDF without blowing RAM?

HTTP body is written in 8 MB aiofiles chunks. Hash streams 64 KB. pypdf walks pages one at a time. Embeddings flush every 16 chunks. Temp file is always unlinked.

Why asyncio.to_thread everywhere?

Qdrant client, SentenceTransformer, and transformers are blocking. to_thread keeps FastAPI able to serve /health and other chats while a model runs. Inference itself is still serialized with locks.

Why locks on embed and rerank?

One model object is not safe for parallel encode. Two in-flight /chat requests would race internal buffers. Embed uses asyncio.Lock; reranker uses threading.Lock around inference_mode.

Why keep a set of asyncio.Task?

create_task without a strong ref can be garbage-collected mid-flight in Python. We add to a set and discard on done. Classic FastAPI footgun.

How do chunks get deleted?

DELETE /documents/{id} → Qdrant filter on document_id → all chunks of that PDF in one op. No per-chunk API. Then BM25 is dropped. Search is correct immediately; HNSW vacuum is later.

After delete, does Qdrant still have the vectors in HNSW?

Yes, internally, for a while. Delete is a soft delete on a bitmask — search skips those points right away. We do not rebuild HNSW per PDF. Qdrant’s vacuum optimizer waits until a segment is ~20% deleted and large enough (~1000 vectors), then rebuilds that segment without the tombstones. That’s storage compaction, not search correctness.

What does “segment” mean in Qdrant?

A storage mini-index inside the collection — like a Lucene segment. Own vectors, payload, HNSW. Vacuum rebuilds a dirty segment, not the whole collection. Not our PDF chunks and not one PDF. One document’s chunks can sit in several segments; one segment can hold many documents. The 20% / 1000 thresholds are per segment.

Why payload indexes and filter-delete?

Dedup and delete are filters on keyword fields. Without indexes Qdrant scans. Delete-by-filter removes every chunk of a document in one op; scroll-delete would silently leave leftovers past the limit.

What does source.score mean?

If rerank is on, it is the cross-encoder logit (can be outside 0–1). If rerank is off, it is Qdrant cosine similarity. Don’t compare them across modes.

Why SSE instead of only sync chat?

Perceived latency. Status events show embedding/search/rerank while work happens; tokens paint immediately. Sync waits for the full DeepSeek completion. UI uses stream.

Apple Silicon?

auto → MPS if available. float16 on GPU-class devices. First boot downloads ~2.3 GB embed + ~1.1 GB rerank into HuggingFace cache, then warmup encodes a dummy string so request #1 is hot.

Why LlamaIndex not LangChain?

We needed PDF nodes, SentenceSplitter, BM25Retriever, and QueryFusionRetriever. LlamaIndex is retrieval-native. We still wrap it — QueryEngine is ours; LlamaIndex does not own the HTTP layer. Honest add: hybrid still leaks a second Qdrant client.

How would you add multi-tenancy?

Auth at the router. Payload field tenant_id + Qdrant filter on every search/scroll/delete. Collection-per-tenant if isolation matters more than ops cost. TaskManager and BM25 become per-tenant or move to Redis/Qdrant sparse.

How would you evaluate quality?

Gold questions with expected pages. Measure recall@k before rerank, nDCG after rerank, faithfulness of answers to context (Ragas/DeepEval — listed on the roadmap). Latency breakdown is already logged per stage.

What happens when things fail?

Bad PDF / empty upload → 400 InvalidPDFError / EmptyUploadError. Qdrant down → 503 VectorDBUnavailableError (dedup fail-fast, not “not a duplicate”). DeepSeek down → 503 LLMUnavailableError. Missing collection on search → empty results. Unknown task → 404. Unexpected → 500 InternalError without traceback in the body.

How many servers are we running?

Two that we start: FastAPI on 8000 and Qdrant on 6333. DeepSeek is a third machine we don’t operate — HTTPS from the app. Embeddings, reranker, BM25, and task status all live inside the FastAPI process. Scale that process to multiple workers and in-memory BM25/tasks split. No Redis/Celery in this repo.

How is it tested?

Unit tests use FakeEmbedder / FakeVectorStore / FakeLLM implementing the same ABCs — no torch, no network. Hybrid tests monkeypatch QdrantClient. Integration job spins Qdrant in GitHub Actions when RUN_INTEGRATION=1. pytest asyncio_mode auto.
